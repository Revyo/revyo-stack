# Starting a product

Inspect the brief and repository, establish the requested outcome, and plan the
implementation before scaffolding a new product. Use the host's Plan mode control
when available. A skill cannot change a host's collaboration mode by declaration:
if no control is exposed, explain that briefly and perform the same discovery and
planning in the current mode. Do not pretend that printing `/plan` or running it
in a shell switched modes. Honor an active host Plan mode's implementation limits.

Ask a small set of consequential questions using the available question tool:
audience and positioning, existing versus new identity, required platforms, and
which product workflows must work now. Inspect supplied references first and ask
only what remains unresolved. Offer useful recommendations. Resolve choices that
would materially change the product before dependent implementation; continue
independent research while awaiting answers. Use stated, reversible assumptions
for incidental details. A sufficiently complete brief needs a plan, not an interview.

Translate the answers into scope, architecture, and observable acceptance criteria.
For a request to build a product, include its functional workflows, data, relevant
authentication, and integrations. Marketing pages alone do not fulfill an app
request. A first vertical slice is an integration checkpoint; continue through the
requested scope rather than declaring that checkpoint the finished product.

If the user explicitly defers the actual app, deliver the brand and marketing
surface, navigation and marketing interactions, SEO/share assets, runnable workspace,
and setup required for that phase. Keep product previews visibly illustrative;
do not add a pretend working scanner, auth flow, or dashboard. Retain a clear path
to the full stack without provisioning unused services or building the deferred app.
Deferral is specific to that request and is not a default for other projects.

In an implementing mode, continue once consequential choices are resolved and the
request authorizes implementation. Do not require another generic confirmation of
the plan. If the host requires an explicit transition out of Plan mode, present the
decision-ready plan and identify that transition rather than claiming to have coded.
